# Шардирование заказов - Документация

## 📋 Обзор архитектуры

Проект реализует горизонтальное шардирование (разделение) данных между двумя базами данных PostgreSQL на основе идентификатора пользователя. Заказы распределяются по шардам по принципу: четные user_id → SHARD_1, нечетные user_id → SHARD_2.

## 🏗️ Архитектурные компоненты

### 1. **Конфигурационные классы (`ru.kuzya.orderservice.config`)**

#### `ShardingConfig` - настройка источников данных
- **Назначение**: Создание и настройка DataSource для каждого шарда
- **Ключевые компоненты**:
    - `shard1DataSource()`: Подключение к SHARD_1 (порт 5437)
    - `shard2DataSource()`: Подключение к SHARD_2 (порт 5438)
    - `routingDataSource()`: Динамический DataSource, который перенаправляет запросы на нужный шард
    - `jdbcTemplate()`: Шаблон для выполнения SQL запросов

#### `ShardContextHolder` - хранение контекста шарда
- **Назначение**: Хранит информацию о текущем шарде в ThreadLocal
- **Методы**:
    - `setShardKey(Shard)`: Устанавливает текущий шард
    - `getShardKey()`: Получает текущий шард
    - `clear()`: Очищает контекст

#### `JpaConfig` - настройка JPA
- **Назначение**: Конфигурация EntityManager и транзакций для работы с routingDataSource

#### `Shard` - перечисление
- `SHARD_1`, `SHARD_2`: Константы для идентификации шардов

### 2. **Уровень контроллера (`ru.kuzya.orderservice.controller`)**

#### `OrderController` - REST контроллер
- **Назначение**: Обработка HTTP запросов
- **Эндпоинты**:
    - `POST /api/orders` - создание заказа
    - `GET /api/orders/{id}` - получение заказа по ID
    - `GET /api/orders/user/{userId}` - получение заказов пользователя
    - `DELETE /api/orders/{id}` - удаление заказа
    - `GET /api/orders` - получение всех заказов

### 3. **Уровень сервисов (`ru.kuzya.orderservice.service`)**

#### `OrderService` - фасадный сервис
- **Назначение**: Координация операций между различными компонентами
- **Основные методы**:
    - `createOrder()`: Создание заказа (использует аспект для определения шарда)
    - `getOrder()`: Получение заказа по ID
    - `getOrdersByUser()`: Получение заказов пользователя
    - `deleteOrder()`: Удаление заказа
    - `getAllOrders()`: Получение всех заказов из всех шардов

#### `ShardOrderService` - сервис для работы с шардами
- **Назначение**: Логика работы с шардированными данными
- **Основные методы**:
    - `saveOrderInTransaction()`: Сохранение заказа в транзакции
    - `findOrderById()`: Поиск заказа по ID во всех шардах
    - `findOrdersByUserInTransaction()`: Поиск заказов пользователя
    - `deleteOrderInShard()`: Удаление заказа из конкретного шарда

### 4. **Уровень репозитория (`ru.kuzya.orderservice.repository`)**

#### `ShardOrderRepository` - репозиторий для работы с шардами
- **Назначение**: Выполнение SQL запросов к конкретным шардам
- **Основные методы**:
    - `getOrdersFromShard()`: Получение всех заказов из шарда
    - `getOrdersFromShardWithFilter()`: Получение заказов с фильтром по ID
    - `deleteOrdersFromShard()`: Удаление заказов из шарда

#### `OrderJpaRepository` - JPA репозиторий
- **Назначение**: Стандартные CRUD операции через JPA
- **Особенность**: Работает через routingDataSource

### 5. **Аспекты (`ru.kuzya.orderservice.aspect`)**

#### `DetermineShardAspect` - аспект для определения шарда
- **Назначение**: Автоматическое определение и установка шарда перед выполнением метода
- **Работает с аннотациями**:
    - `@DetermineShard`: Помечает методы, где нужно определить шард
    - `@ShardKey`: Помечает параметр (userId) для определения шарда

## 🔄 Потоки выполнения

### 1. **Создание заказа**

```
OrderController.createOrder()
    ↓
OrderService.createOrder() (@DetermineShard)
    ↓
DetermineShardAspect.beforeMethod()
    ↓ Определение шарда: userId % 2 == 0 ? SHARD_1 : SHARD_2
    ↓ ShardContextHolder.setShardKey(shard)
    ↓
ShardOrderService.saveOrderInTransaction()
    ↓
OrderJpaRepository.save() (через routingDataSource)
    ↓
RoutingDataSource.determineCurrentLookupKey()
    ↓
ShardContextHolder.getShardKey() → возвращает нужный шард
    ↓
Подключение к соответствующей базе данных
    ↓
Сохранение заказа
```

### 2. **Получение заказа по ID**

```
OrderController.getOrder()
    ↓
OrderService.getOrder()
    ↓
ShardOrderService.findOrderById()
    ↓
Установка SHARD_1 → поиск в первом шарде
    ↓ Если не найдено
    ↓
Установка SHARD_2 → поиск во втором шарде
    ↓ Если не найдено → исключение
    ↓
ShardOrderRepository.getOrdersFromShardWithFilter()
    ↓ Для каждого шарда:
        ShardContextHolder.setShardKey(shard)
        ↓
        JdbcTemplate.query() → выполнение SQL
        ↓
        RoutingDataSource выбирает нужный DataSource
```

### 3. **Динамический выбор источника данных**

```
Запрос к базе данных
    ↓
JdbcTemplate или JPA
    ↓
RoutingDataSource (AbstractRoutingDataSource)
    ↓
determineCurrentLookupKey()
    ↓
ShardContextHolder.getShardKey()
    ↓ Возвращает SHARD_1 или SHARD_2
    ↓
RoutingDataSource выбирает соответствующий DataSource
    ↓
Подключение к нужной базе данных
```

## 📊 Логика распределения данных

### Определение шарда:
```java
// Простая стратегия на основе userId
if (userId % 2 == 0) {
    return Shard.SHARD_1;  // Четные пользователи
} else {
    return Shard.SHARD_2;  // Нечетные пользователи
}
```

### Преимущества:
1. **Равномерное распределение** - примерно 50/50 между шардами
2. **Предсказуемость** - легко определить, где находится заказ
3. **Простота реализации** - минимальная сложность логики

## 🛠️ Конфигурация базы данных

### SHARD_1:
- **URL**: `jdbc:postgresql://localhost:5437/order_db`
- **Порт**: 5437
- **Стратегия**: Четные userId

### SHARD_2:
- **URL**: `jdbc:postgresql://localhost:5438/order_db`
- **Порт**: 5438
- **Стратегия**: Нечетные userId

## 🔧 Настройки транзакций

### Транзакционные границы:
1. **Создание заказа**: `Propagation.REQUIRES_NEW` - всегда новая транзакция
2. **Поиск заказа**: `readOnly = true` - транзакция только для чтения
3. **Удаление заказа**: Без явных транзакций, управляется на уровне сервиса

### Особенности:
- `@Transactional` работает с `routingDataSource`
- Транзакции переключаются между шардами автоматически
- ThreadLocal гарантирует изоляцию контекста между потоками

## 📝 Примеры использования

### Создание заказа:
```http
POST /api/orders
Content-Type: application/json

{
    "userId": 123,
    "productName": "Laptop",
    "quantity": 1
}
```
**Результат**: Заказ сохраняется в SHARD_2 (т.к. 123 нечетное)

### Получение заказа:
```http
GET /api/orders/749f1f5c-10b6-46cb-a422-a6976b1958fa
```
**Процесс**: Поиск сначала в SHARD_1, затем в SHARD_2

### Удаление заказа:
```http
DELETE /api/orders/749f1f5c-10b6-46cb-a422-a6976b1958fa
```
**Процесс**: Попытка удаления из SHARD_1, если не найден - из SHARD_2

## 🎯 Ключевые принципы

1. **Прозрачность**: Приложение скрывает сложность шардирования от пользователя
2. **Расширяемость**: Легко добавить новые шарды
3. **Отказоустойчивость**: Поиск во всех шардах при операциях чтения
4. **Производительность**: Параллельные запросы к разным шардам
5. **Масштабируемость**: Распределение нагрузки между базами данных

## ⚠️ Важные замечания

1. **Согласованность**: При удалении проверяются оба шарда
2. **Производительность**: Поиск по ID требует проверки всех шардов
3. **Транзакции**: Сложные транзакции, затрагивающие несколько шардов, не поддерживаются
4. **Миграция**: Перемещение данных между шардами требует дополнительной логики

## 🔮 Возможные улучшения

1. **Кеширование**: Кеширование соответствия ID заказа и шарда
2. **Мониторинг**: Статистика распределения и нагрузки
3. **Балансировка**: Динамическое перераспределение данных
4. **Репликация**: Реплики для каждого шарда для отказоустойчивости

Эта архитектура демонстрирует практическую реализацию шардирования в Spring Boot приложении с использованием динамического выбора источника данных и ThreadLocal для управления контекстом шардинга.
